# NAVISOMA Native C/C++ Integration Plan

## Purpose

This document turns NAVISOMA's "reuse C/C++ before reimplementation" principle into a concrete implementation plan. The goal is to remove open-ended research from the implementation phase: for each major subsystem, it defines the native asset to reuse, how Nim should call it, where generated code or a shim is required, how ownership/errors/threading are handled, and how the dependency is acquired and tested.

The governing rule is:

```text
existing C/C++ implementation
        |
        v
smallest maintainable ABI boundary
        |
        v
Nim-safe facade
        |
        v
NAVISOMA semantic/backend layer
```

NAVISOMA does not expose foreign object graphs into the product core. C/C++ details terminate at an integration boundary.

## Locked architectural decisions

The following decisions should be treated as defaults unless a concrete compatibility failure is demonstrated.

1. **Prefer C ABI at the Nim boundary.** Even when the implementation is C++, a narrow `extern "C"` facade is preferred over exposing a large C++ API graph directly.
2. **Use direct `importc` for stable public C APIs.** WSLC is the primary example.
3. **Use generated C++ protobuf/gRPC code behind a project-owned C facade for containerd and BuildKit.** Do not implement protobuf or gRPC wire protocols in Nim.
4. **Use NimYAML for YAML.** It is already a stable Nim YAML 1.2 implementation and avoids an unnecessary native dependency.
5. **Use an existing C++ JSON Schema implementation behind a tiny C facade.** `jsoncons` is the current first choice for Draft 2020-12 validation.
6. **Do not implement HTTP/2, HPACK, TLS, gRPC transport, protobuf encoding, CNI, OCI low-level runtime execution, or VM technology in NAVISOMA.**
7. **Generated ABI bindings are committed to source control.** Binding generators are regeneration-time tools, not normal build dependencies.
8. **Pin every native SDK/library version and provenance.** A header/version update and regenerated bindings must land atomically.

## Why the default Nim backend should remain C-oriented

Nim can generate both C and C++. Direct `importcpp` is useful, but using the C++ backend globally would unnecessarily expose the entire NAVISOMA binary to C++ ABI/compiler/runtime choices.

The preferred architecture is therefore:

```text
NAVISOMA Nim core
    |
    | importc
    v
project-owned C ABI
    |
    +-- direct upstream C API
    |
    +-- C++ shim -> C++ library / generated C++ code
```

This preserves a simple Nim-facing ABI and permits native C++ dependencies to be built independently with CMake/MSVC/Clang/GCC as appropriate.

Direct `importcpp` remains acceptable for narrowly contained header-only integrations or experiments, but it is not the default product boundary.

Nim's official backend documentation confirms C and C++ code generation (`nim c`, `nim cpp`): https://nim-lang.org/docs/backends.html

## Standard repository layout for native integration

The main repository should converge on a predictable native layout:

```text
native/
  cmake/
  grpc/
    generated/          # generated .pb.cc/.pb.h/.grpc.pb.cc/.grpc.pb.h
    shim/               # NAVISOMA C ABI over generated C++ API
  containerd/
    proto/              # pinned upstream proto source or manifest of source revision
    generated/
    shim/
  buildkit/
    proto/
    generated/
    shim/
  jsonschema/
    shim/
  wslc/
    generated/          # generated Nim ABI bindings from wslcsdk.h
    metadata/           # pinned SDK version/hash/ABI manifest

src/
  native/               # raw Nim importc declarations / loader helpers
  bindings/             # safe Nim ownership wrappers
  backends/             # NAVISOMA semantic lowering
```

Generated files must contain an autogenerated header with upstream version/hash and generator version.

## Binding generation policy

### C headers

Do not manually copy large C structs/enums/function declarations unless the API is tiny and stable. For nontrivial headers, use a Clang-semantic binding generator.

Futhark is the leading Nim-side candidate because it uses Clang to resolve C semantics, macros and conditional compilation: https://github.com/PMunch/futhark

However, NAVISOMA's production rule is broader than a particular generator:

- generator version is pinned;
- input header hash is pinned;
- generated Nim is committed;
- compile-time `sizeof`/alignment/offset checks are added for ABI-critical structs;
- regeneration only occurs on intentional SDK upgrades;
- normal users/builders do not need Clang/binding-generator tooling merely to compile NAVISOMA.

Microsoft's MXC WSLC implementation follows exactly this model with Rust bindgen: generated bindings from `wslcsdk.h` are committed, and SDK drift is intentionally surfaced during regeneration/build rather than discovered as runtime memory corruption: https://github.com/microsoft/mxc/blob/main/docs/wsl/wslc-sdk-bindings.md

### C++ APIs

For C++ dependencies, avoid generating a large Nim C++ binding unless direct use provides clear value. Preferred pattern:

```cpp
// navisoma_xxx.h
#ifdef __cplusplus
extern "C" {
#endif

NvsmHandle* nvsm_xxx_create(...);
int nvsm_xxx_operation(NvsmHandle*, ...);
void nvsm_xxx_destroy(NvsmHandle*);

#ifdef __cplusplus
}
#endif
```

Internally, the implementation owns `std::unique_ptr`, protobuf messages, gRPC stubs, exceptions and templates. None cross into Nim.

## Common ABI rules

### Handles

Opaque pointer handles are the standard cross-language ownership mechanism.

```c
typedef struct nvsm_containerd_client nvsm_containerd_client;
```

Nim treats these as opaque pointer types. Every creating call has one matching destroy/release call.

### Strings

Do not pass `std::string` across the ABI. Use UTF-8 `const char* + size_t` for input. For output, either:

- caller-provided buffers; or
- owned result handles with accessor + release functions.

Never require Nim to free memory allocated by a C++ allocator unless the same native component provides the release function.

### Byte buffers

Use pointer + length. For streaming output, use callbacks or result handles. Keep protobuf/gRPC byte buffers behind the shim.

### Errors

No C++ exception crosses the C ABI. Every exported shim function catches all exceptions and returns an explicit status.

Preferred model:

```c
typedef struct {
  int32_t code;
  const char* message;
  size_t message_len;
} nvsm_error_view;
```

The actual message is owned by a request/result handle until released.

At the Nim layer, translate into the NAVISOMA error taxonomy (`RuntimeError`, `BuildError`, `CapabilityError`, etc.).

### Callbacks

Callbacks crossing into Nim must document:

- which thread invokes them;
- whether invocation is reentrant;
- whether the data remains valid after callback return;
- cancellation behavior;
- ordering guarantees.

A callback must not retain Nim GC-managed pointers in C/C++ without an explicit rooted ownership mechanism. Prefer copying callback payloads into Nim-owned values at the boundary.

### Threading

Do not allow upstream worker threads to invoke arbitrary NAVISOMA semantic logic. Native callbacks should enqueue compact events into a NAVISOMA-owned event queue; planner/backend logic consumes those events on controlled Nim threads/tasks.

## WSLC: concrete integration

### Upstream asset

WSL Containers exposes a first-party C API through the WSLC SDK. Microsoft documents C, C# and C++ projections. The SDK is delivered in the `Microsoft.WSL.Containers` package; the C++/WinRT projection is still preview: https://learn.microsoft.com/en-us/windows/wsl/wsl-container

Microsoft MXC provides the strongest current source-level integration reference. Its documentation records that the SDK provides:

- `wslcsdk.h`
- `wslcsdk.lib`
- `wslcsdk.dll`

and that its Rust backend calls the C ABI directly. See:

- https://github.com/microsoft/mxc/blob/main/docs/wsl/wsl-container-support-plan.md
- https://github.com/microsoft/mxc/blob/main/docs/wsl/wslc-sdk-bindings.md

### NAVISOMA boundary

WSLC should be the simplest native integration:

```text
Nim safe wrapper
   |
importc / generated bindings
   |
wslcsdk.h ABI
   |
wslcsdk.dll
```

No C++/WinRT layer is required for the initial backend.

### Binding source of truth

Use the exact `wslcsdk.h` from the pinned SDK package as the source of truth. Do not hand-maintain struct layouts.

For every SDK bump:

1. bump pinned package version;
2. verify package SHA-256;
3. extract `wslcsdk.h`, import library and runtime DLL for target architecture;
4. regenerate Nim raw bindings;
5. compile ABI size/alignment assertions;
6. update only the safe facade/call sites affected by API drift;
7. run WSLC E2E tests on a live Windows + WSL host;
8. commit version/hash/generated bindings together.

### Required API families

The current MXC reference demonstrates the practical API set NAVISOMA should expect to bind:

**Preflight/service**
- missing-component check;
- service/version query;
- install/dependency checks where supported.

**Session**
- initialize session settings;
- CPU/memory/timeout/feature flags;
- create/release/terminate session;
- image listing/pull operations.

**Container**
- initialize container settings from image;
- volumes;
- network mode;
- port mappings;
- flags;
- init-process assignment;
- create/start/stop/delete/release;
- retrieve init process.

**Process**
- initialize process settings;
- command line, environment, working directory;
- I/O handles;
- exit event/exit code;
- release process.

MXC also confirms that stdout/stderr can be exposed as Win32 `HANDLE`s, allowing normal Win32 `ReadFile`/wait primitives rather than inventing a gRPC stream bridge.

### Known capability caveat

The SDK is evolving. MXC records at least one example where UDP port mapping is declared but runtime support returns `E_NOTIMPL`. Therefore NAVISOMA must gate features through an explicit capability/version layer rather than assuming header presence equals runtime support.

### DLL loading

Prefer secure explicit loading from NAVISOMA-controlled paths rather than ambient DLL search order. The native-dependency layer must record which `wslcsdk.dll` version is staged with a release and must avoid DLL-preloading/hijack-prone search behavior.

## protobuf: concrete integration

### Upstream asset

Use the official Protocol Buffers C++ runtime and official `protoc` C++ generation. The generated code guide states that each `.proto` generates `.pb.h` and `.pb.cc` through `--cpp_out`: https://protobuf.dev/reference/cpp/cpp-generated/

### Why C++ generated code, not a Nim protobuf runtime

containerd and BuildKit schemas are upstream-owned and versioned. NAVISOMA gains little by owning another protobuf language runtime. The official runtime provides parsing, serialization, descriptors, reflection and modern proto/Editions support.

### Generation

For each pinned upstream proto set:

```text
protoc -I <imports> --cpp_out=<generated> <files...>
```

Generated output is compiled into the native bridge library. Normal NAVISOMA builds do not need to parse `.proto` dynamically.

### ABI boundary

Generated protobuf message classes stay in C++. The C facade exposes NAVISOMA operations, not message getters/setters one field at a time.

Bad boundary:

```text
Nim -> hundreds of generated protobuf class methods
```

Preferred boundary:

```text
Nim runtime action
  -> C facade operation
     -> generated protobuf request/response internally
```

This isolates upstream schema churn from Nim source.

## gRPC: concrete integration

### Upstream asset

Use official gRPC C++/Core. gRPC officially supports C/C++ on Linux, macOS and Windows: https://grpc.io/docs/

For generated C++ clients, use the standard gRPC toolchain:

```text
protoc --cpp_out=<generated> ...
protoc --grpc_out=<generated> --plugin=protoc-gen-grpc=<grpc_cpp_plugin> ...
```

The official C++ tutorial documents this code-generation pattern: https://grpc.io/docs/languages/cpp/basics/

### Transport requirement

containerd normally listens on `/run/containerd/containerd.sock`; BuildKit normally listens on `/run/buildkit/buildkitd.sock`. gRPC's official target naming supports Unix-domain sockets using `unix:path` or `unix:///absolute_path`: https://github.com/grpc/grpc/blob/master/doc/naming.md

Therefore the C++ gRPC client path can address both default daemon sockets without writing a custom socket transport.

### NAVISOMA boundary

Do **not** wrap the entire gRPC C API in Nim first. For containerd and BuildKit, generated C++ stubs already know the RPC service/method/message types. Build one project-owned C ABI around the operations NAVISOMA requires.

Use gRPC Core C directly only where a generic transport abstraction provides a measured advantage over generated C++ stubs.

### Async and streaming

Generated C++ client code and gRPC C++ async/callback APIs remain native. The shim converts native events into a stable C callback/event API.

Do not pass `grpc::CompletionQueue`, `grpc::ClientContext`, protobuf message classes, or C++ callback objects into Nim.

## containerd: concrete integration

### Upstream assets

- containerd public protobuf service definitions under `api/services/...`;
- official containerd behavior/client code as semantic reference;
- official daemon endpoint, normally `/run/containerd/containerd.sock`.

containerd's operations documentation confirms the normal gRPC socket path. Its getting-started client documentation also demonstrates namespaces as a required caller concern.

Sources:

- https://github.com/containerd/containerd/tree/main/api
- https://github.com/containerd/containerd/blob/main/docs/getting-started.md
- https://github.com/containerd/containerd/blob/main/docs/ops.md

### Native generation model

```text
containerd upstream .proto
     |
protoc + grpc_cpp_plugin
     |
C++ protobuf/gRPC generated client
     |
navisoma_containerd C++ facade
     |
extern C API
     |
Nim containerd binding
     |
NAVISOMA runtime backend
```

### Service scope

The facade should be generated/implemented only for service groups proven necessary by NAVISOMA's runtime actions. Expected groups include:

- namespaces;
- containers;
- images;
- content;
- snapshots;
- tasks/processes;
- leases;
- events;
- diff/introspection as required by image/snapshot workflows.

Do not expose every containerd RPC preemptively.

### Namespace handling

containerd namespaces are part of the client contract. NAVISOMA should assign a deterministic project/tool namespace strategy and inject namespace metadata inside the native facade so callers cannot accidentally omit it.

### High-level operation composition

The facade should expose semantic operations larger than one raw RPC where containerd requires coordinated calls. Example shape:

```c
nvsm_cd_image_pull(...)
nvsm_cd_container_create(...)
nvsm_cd_task_start(...)
nvsm_cd_exec_start(...)
nvsm_cd_task_stop(...)
nvsm_cd_container_remove(...)
```

The exact sequence must be traced from containerd's official Go client and nerdctl, not invented from proto names alone.

## BuildKit: concrete integration

### Upstream assets

BuildKit exposes a gRPC API and uses LLB/protobuf as its low-level build model. `buildctl` connects to `buildkitd`; the default address is `unix:///run/buildkit/buildkitd.sock`: https://github.com/moby/buildkit/blob/master/docs/reference/buildctl.md

Use upstream protobuf definitions and generated C++ gRPC code rather than implementing BuildKit RPC serialization.

### NAVISOMA boundary

```text
Compose build semantics / BuildAction
      |
Nim BuildKit facade
      |
C ABI
      |
C++ generated BuildKit gRPC/protobuf client
      |
buildkitd
```

### Required responsibilities

The native facade is expected to own only transport/client mechanics and generated message handling. NAVISOMA owns:

- Compose `build:` lowering;
- build context selection;
- frontend/options mapping;
- cache import/export semantics exposed to users;
- secret/SSH mapping;
- solve/progress normalization;
- result identity and handoff to OCI/runtime workflows.

BuildKit owns the solver and workers.

### Streaming/session warning

BuildKit uses streaming/progress/session-related behavior beyond a single unary `Solve`. The C facade must therefore be event/callback capable from the beginning; do not design an API that assumes every RPC returns one immediate response.

## JSON Schema: concrete integration

### Upstream asset

`jsoncons` is header-only C++ and supports JSON Schema including Draft 2020-12. Use it as the default validator candidate rather than building a Nim JSON Schema engine.

Project: https://github.com/danielaparker/jsoncons

### Boundary

Do not expose `jsoncons::json` or validator classes to Nim. Create a tiny C++ module:

```c
nvsm_schema* nvsm_schema_compile(const char* schema_json, size_t len, nvsm_error*);
int nvsm_schema_validate(nvsm_schema*, const char* document_json, size_t len, nvsm_validation_result*);
void nvsm_schema_destroy(nvsm_schema*);
```

Return structured validation paths/messages through a result handle.

### Use in Compose

NimYAML produces the parsed Compose representation. For schema validation, convert the relevant canonical/raw tree to JSON text or a compact neutral representation and pass it through the schema facade. Compose-specific semantic checks remain in Nim.

## YAML: concrete integration

Use NimYAML directly through Nimble unless conformance testing finds a blocking Compose-relevant incompatibility.

Project: https://github.com/flyx/NimYAML

NimYAML reports stable status and passing the current YAML 1.2 test suite. This is the rare case where a native Nim dependency is already simpler than adding C/C++ glue.

## OCI and registry integration

### OCI models

Descriptors, manifests, image indexes, image config, platform and digest types are sufficiently small that NAVISOMA may define its minimal typed vocabulary directly in Nim. Do not add a C++ dependency solely to hold JSON data structures.

Use upstream OCI schemas/specifications as the contract and conformance source.

### Registry

Do not write HTTP/TLS. Prefer libcurl or another mature native HTTP stack if the existing Nim HTTP ecosystem does not satisfy large streaming/auth/retry needs.

The NAVISOMA-owned portion is OCI/Docker Distribution behavior:

- auth challenge/token flow;
- media-type negotiation;
- manifests;
- blob transfer;
- resumable upload;
- digest verification;
- referrers/tags;
- retry/redirect policy.

ORAS, `go-containerregistry` and `containers/image` remain behavioral references even when their Go code is not linked.

## CNI, runc/crun and Lima

These are process/system boundaries, not library-reimplementation targets.

- CNI: use existing plugin binaries/configuration through containerd/nerdctl-compatible behavior.
- runc/crun: reach through containerd or another runtime manager.
- Lima: invoke/manage an existing Lima installation/VM lifecycle on macOS; connect to the runtime in the guest. Do not implement virtualization or filesystem sharing.

## Native dependency acquisition

Every native dependency must have one source-of-truth manifest containing at least:

```text
name
upstream URL
version/tag/commit
source/package SHA-256
license
build system
required compile options
produced library names
supported target architectures
runtime files that must be shipped
security update policy
```

### Preferred acquisition hierarchy

1. official binary/SDK package with pinned hash when the vendor publishes a stable package (WSLC);
2. reproducible source build from pinned tag/commit (gRPC/protobuf and project shims);
3. system package only as an opt-in developer convenience, not the sole reproducible release path.

### Native build system

Use a small CMake project for NAVISOMA-owned C/C++ shims and generated C++ code. CMake is already the standard documented build path for gRPC C++ and works with GCC/Clang/MSVC.

The Nim build should consume the produced library and headers rather than embed ad-hoc compiler invocations throughout Nim source files.

## Static versus dynamic linking

Default preference:

- **project-owned shims:** static link;
- **gRPC/protobuf/jsoncons-generated bridge:** static link where license/platform/toolchain constraints permit;
- **WSLC:** load/use the vendor SDK DLL as required by the platform;
- **system daemons:** process/socket boundary, never link their implementation into NAVISOMA.

A native library may move to dynamic linkage when binary size, upstream redistribution requirements, CVE servicing, or OS conventions make it preferable. This is a release-engineering decision, not an ABI-design change because Nim still targets the project C facade.

## ABI/version validation

For each native facade, tests must cover:

- expected upstream version;
- `sizeof`/alignment for exposed structs;
- enum/constants used by the facade;
- symbol existence;
- create/use/destroy lifecycle;
- error path ownership;
- callback after cancellation/destroy;
- multi-thread behavior where upstream callbacks are threaded;
- real I/O, not mocked results;
- resource-leak detection in repeated lifecycle loops.

WSLC requires live-host tests because the runtime is Windows/WSL-specific. containerd/BuildKit require tests against real daemon versions matching the support matrix.

## Platform build matrix

### Linux

- Nim C backend with GCC or Clang;
- CMake native bridge build with GCC/Clang;
- gRPC/protobuf static/native libraries;
- containerd/buildkitd connected through Unix-domain sockets.

### WSL

Same Linux native stack. Treat WSL as a Linux execution environment at this layer; Windows/WSLC is a different backend below the same NAVISOMA model.

### macOS

- NAVISOMA host binary built natively on macOS;
- macOS-only orchestration/VM lifecycle uses existing Lima tooling;
- actual Linux containerd/BuildKit API may be reached through the managed Linux VM connection/forwarding strategy;
- native host libraries required by NAVISOMA must build for Apple Silicon and supported Intel macOS where support is claimed.

### Windows

- Nim with MSVC-compatible C ABI;
- WSLC direct C binding against pinned WSLC SDK;
- Win32 `HANDLE`/HRESULT/error conversion isolated in WSLC binding layer;
- x64 and ARM64 SDK packages/bindings validated independently where supported.

## What implementation should *not* have to research again

Before production coding starts, the following are considered settled directions:

| Area | Implementation direction |
|---|---|
| YAML | NimYAML |
| Compose semantics | NAVISOMA-owned Nim code, compose-go/reference behavior as oracle |
| JSON Schema | jsoncons C++ behind C facade |
| protobuf | official C++ runtime + `protoc` generated C++ |
| gRPC | official gRPC C++/Core, generated C++ stubs behind C facade |
| containerd | upstream `.proto` + generated C++ + C facade + Nim semantic backend |
| BuildKit | upstream `.proto`/LLB + generated C++ + C facade + Nim build backend |
| WSLC | generated/direct C binding to `wslcsdk.h`/`wslcsdk.dll` |
| CNI | reuse existing plugins via runtime infrastructure |
| runc/crun | reuse through runtime manager |
| macOS VM | Lima or equivalent mature existing VM layer |
| OCI models | minimal Nim typed vocabulary from upstream specs |
| Registry HTTP/TLS | existing mature HTTP/TLS stack; NAVISOMA owns distribution semantics only |

Implementation work may still uncover upstream bugs or version-specific incompatibilities, but it should not reopen the basic question of whether NAVISOMA should implement these mature foundations from scratch.

## Remaining validation tasks before coding expands

These are bounded validation tasks, not open-ended architecture research:

1. Run the WSLC header-to-Nim binding regeneration pipeline on the pinned SDK and verify ABI assertions on x64/ARM64 where available.
2. Generate one containerd C++ service client and prove a unary call over `unix:///run/containerd/containerd.sock` through the C facade.
3. Prove a containerd streaming/event path through the facade.
4. Generate BuildKit Control client code and prove solve/status or equivalent streaming behavior through the same facade architecture.
5. Compile jsoncons validation facade on Windows/Linux/macOS and execute official Draft 2020-12 validation fixtures relevant to Compose.
6. Finalize native dependency CMake presets/toolchain files and artifact/cache layout.

Once these six validations pass, production implementation should proceed from this document rather than re-evaluating protocol/library choices issue by issue.
